# Event sourcing & projection fixes: case-engine lessons for Bounded

Oct 18, 2026 · @Olger Warnier · revised after validation against the code

## Summary

**Status (Nov 4, 2026): all 22 backlog items are done.** Items 1–14, 16, 18 and 21 are on `main` through #77 and #79 (item 13 was replaced by the required aggregate type of item 21). Items 15, 17, 19, 20 and 22 are in the commits after #79 (clustering, `bounded-pekko-projection` and its store factories). The text below is the original analysis; each backlog row ends with what was delivered. Combined logic testing and deadlines continue in [combined-logic-testing-deadlines-and-time.md](combined-logic-testing-deadlines-and-time.md).

Bounded still has 15 of the 20 generic event-sourcing and projection bugs that case-engine fixed between 2020 and October 2026, plus 14 found while checking. Six are P1 because they lose events or report success for writes that never happened:

- **Classic aggregates reply `Ok` before persisting** and do not handle persist failures (W1, W2).
- **Projections never restart**: one failure stops a materializer until the JVM restarts (R1).
- **Offset saves are fire-and-forget**: failures are swallowed and the offset can move backwards (R2).
- **Combined logic shares one offset across tags and only reads the first two tags**, so a restart can skip events (R3, B1).
- **Gateways lose or duplicate aggregates**: classic gateways keep routing to dead aggregates and can start two actors for one id; all gateways drop or double commands that arrive while an aggregate is being passivated (W3, B5, B11).
- **The Cassandra offset store does not work with Pekko's config**: it reads a keyspace path that does not exist, and writes offsets to a different keyspace than it reads them from (B9).

Bounded was single-node only: neither command handling nor event materializers could run safely on more than one node (B14, R9), and replies had no cluster serialization (W7). Items 15, 17 and 22 fixed that. Typed aggregates avoid most write-side issues; the read side affects both. The backlog has 22 items in three milestones plus a group for running clustered, numbered in the order they should be done (see [Order of work](#order-of-work)). Breaking changes are collected so they can land in 0.4.0, the first Pekko release, which users have to migrate to anyway.

## Method

The case-engine history was searched for commits that touch event sourcing (persistent actors, recovery, snapshots, serialization, journals) and projections (read journal queries, offsets, replay, materializer restarts). Each fix was then compared with the matching code in bounded-framework.

- Source: `casefabric/case-engine` git log, commit messages plus diffs. All cited commit hashes were checked to exist and match the fix they are cited for.
- Target: `bounded-core` (aggregates, gateways, `eventmaterializers/`, offset stores) and `bounded-test`, at commit `f2f52fe` on `pekko_migration` (`bounded-core` on `review_fixes` is identical).
- The analysis itself changed no code; every fix was listed as a backlog item, and all have since been implemented (see the status above).

## Design decision: one offset record per event materializer

Every event materializer keeps exactly one offset record, keyed by its `viewIdentifier`. That is already true for single-tag materializers and stays so. For a combined logic that reads several tags, the record holds a position per tag rather than a single offset:

- A single offset cannot be correct for several tags. On LevelDB the tag offsets are separate counters and cannot be compared at all. On journals with comparable offsets (JDBC global ordering, Cassandra time UUIDs, R2DBC timestamps), `Merge` interleaves the streams, so the last handled offset can be ahead of events still pending in the slower tag. A low-water mark would only work on the ordered journals, and it still needs per-tag tracking in memory.
- So the record's value becomes a per-tag map (`tag -> Offset`), saved as one value in one row under `viewIdentifier`. The materializer rewrites the whole map after each event; it is small.
- Representation: a Bounded `TagOffsets(Map[String, Offset])` that extends Pekko's `Offset`, so the `OffsetStore` and `Resumable.registerListener(Option[Offset])` signatures stay as they are. This is possible because `org.apache.pekko.persistence.query.Offset` is a plain `abstract class`, not sealed (checked in the sources of Pekko 1.7.0, the version in `Dependencies.scala`, and of 2.0.0-M1). `TagOffsets` stays inside Bounded: the combined logic hands each tag's own offset to `eventsByTag`, so no journal ever receives a `TagOffsets`.
- Compatibility: a stored plain offset (the current format) is read as the start offset for every tag, which is what happens today, and is rewritten as `TagOffsets` after the first event. No key changes, so no stored offsets are orphaned. Older Bounded versions cannot read the new value, so there is no downgrade after upgrading.
- Store encoding: each store gets an offset type `tags`, with a value that escapes tag names. The shared offset encoder (backlog 4) adds it to every store before the combined logic starts writing it (backlog 7).
- Alternative for new combined logic: give the combined logic its own tag (with the classic `tags` hook from backlog 12, or `withTagger` on typed aggregates). The combined logic then reads one stream with one plain offset. Document this as the preferred way; `TagOffsets` keeps existing multi-tag combined logic correct.

## Design decision: Pekko Projections

Bounded's materializers could be rebuilt on Pekko Projections (`pekko-projection-core` and `-eventsourced` are already dependencies of `bounded-core`, unused in `src/main`). That would bring restart, batching, exactly-once handlers, `ProjectionManagement` and the `ShardedDaemonProcess` pattern, but a full switch is a major release: Projections has no pluggable offset store (Bounded's stores, `OffsetCodec` and the LMDB and in-memory stores for node-local read models would go; every user migrates stored offsets, e.g. with `ProjectionManagement.updateOffset`), it has no separate replay phase (`replayEvents`, `handleReplayEvent`, replay-then-stop), it does not store an offset only on request (`withPartialReplay = false`), a multi-tag combined logic becomes one projection per tag or a custom source, and it does not solve the R2DBC journal by tag (item 21 selects by entity type instead).

**Decision:** add, do not replace. Item 19 adds an adapter that runs a Bounded handler as a Pekko Projection, in an optional module; the current materializers stay as they are. New read models that need exactly-once results or a single runner in a cluster use the adapter; everything else keeps working. Revisit a full switch for a later major release, when the adapter has been used and if the current pipeline becomes a burden.

## Design decision: entity types on the R2DBC journal

The R2DBC journal (`pekko-persistence-r2dbc`) stores tags but cannot query by them. Its read side is built on slices of an entity type: `eventsBySlices(entityType, minSlice, maxSlice, offset)` runs `WHERE entity_type = ? AND slice BETWEEN …`. The entity type is the part of the persistence id before `|` (`PersistenceId.extractEntityType`), stored in its own column when the event is written. Checked in the sources of plugin 1.2.0 and 2.0.0-M1.

Options considered for item 21:

- **Bounded's own tag SQL** (the earlier plan): `WHERE $1 = ANY(tags)`. Keeps tags as the selector, but Bounded has to write and maintain the late-event handling (behind-current-time, backtracking window, deduplication), and the plugin's schema has no index on `tags`.
- **Wait for Pekko 2.0:** plugin 2.0.0-M1 fills `tags` on slice envelopes, but still has no `eventsByTag`, so a materializer would read every slice of an entity type and filter by tag anyway. Pekko 2.0 is at milestones (2.0.0-M4) and `pekko-projection`, `pekko-persistence-cassandra` and `pekko-persistence-inmemory` have no 2.0 release yet, so Bounded cannot move.
- **Entity type instead of tag (chosen):** use the query the plugin is built for. Works on plugin 1.2.0 and Pekko 1.x today, because the empty `tags` on 1.x envelopes no longer matter.

**Decision:** on the R2DBC journal a materializer selects by entity type. Users do not choose between tag and entity type: Bounded introduces one concept, the **aggregate type**, and maps it per journal (see [Aggregate type](#aggregate-type-tag-or-entity-type-hidden-from-users) below). This assumes one tag per aggregate root type, which is what the tag and the entity type then both express.

Effects:

- **Coarser selection.** An entity type is all events of one aggregate type. A tag on a subset of a type's events, or one tag across types (e.g. `aggregate` on everything), has no R2DBC equivalent: read the type and drop the rest with `MaterializerEventFilter`, or list several types in a combined logic.
- **Every persistence id carries the type.** The aggregate type is required for classic and typed aggregates, and Bounded builds `type|id` itself, so there is no aggregate without an entity type. Journals written by Bounded 1.0.0 or earlier (unprefixed ids, or a `persistenceIdPrefix` other than `type|`) are converted once with `AggregateTypeMigration` (see [Migrating existing journals](#migrating-existing-journals-aggregatetypemigration)).
- **Offsets:** `TimestampOffset`, already handled by `OffsetCodec` (including its `seen` map) and `R2dbcOffsetStore`. An offset stored from a tag-based run on another journal means nothing here: the materializer replays once.
- **Gains:** the plugin's own query engine (late events, backtracking, optional `publish-events` for low latency on the writing node), its existing slice index instead of a `GIN (tags)` index, and a later way to split one materializer over nodes by slice range (items 15, 22).
- **Tags become unused on R2DBC.** They are still written, but nothing reads them there.
- **The type name is permanent.** It is part of every persistence id, so renaming a type means migrating ids (a tag rename only affected new events).

### Aggregate type: tag or entity type hidden from users

People building an aggregate, combined logic or projection name an aggregate type and never see tags, entity types or slices. **Every aggregate has one**: it is required, there is no default and no opt-out.

- **The name:** `final case class AggregateType(name: String)`, validated (non-empty, no `|`), defined once per aggregate (`object Order { val Type = AggregateType("order") }`) and used on both sides, so a typo does not compile into an empty materializer. No default from the class name: renaming or moving a class would change every persistence id, two classes with the same simple name in different packages would share streams (W4), and JVM names of Scala objects, nested and anonymous classes are unreliable (`Order$`, `$anon`).
- **Classic write side:** `AggregateRootActor` gets an abstract `def aggregateType: AggregateType`, so a classic aggregate without one does not compile. `persistenceId` becomes final and is `s"${aggregateType.name}|$aggregateId"`; on tag-based journals every event is persisted as `Tagged(event, Set(aggregateType.name) ++ tags(event))`, so they select by the type as well; on R2DBC an event is wrapped only when `tags(event)` is non-empty (decided after review: no `Tagged` where it is not needed, so write-side event adapters keep working there). Aggregate ids may contain `|`: the persistence id is built as a plain string, because Pekko's `PersistenceId(type, id)` refuses them. `persistenceIdPrefix` (item 13, released in 1.0.0) is removed: a 1.0.0 aggregate with prefix `"order|"` sets `aggregateType = AggregateType("order")` and keeps its persistence ids; any other prefix (or none) is converted by the migration. `tags(event)` (item 12) stays for extra tags, which only tag-based journals can query.
- **Typed write side:** the gateway only receives a `Behavior[T]`, so Bounded cannot change the persistence id or tagger of an `EventSourcedBehavior` it is handed. Instead Bounded hands out the identity: `TypedAggregateRootManager` gets `def aggregateType: AggregateType = AggregateType(entityTypeKey.name)` (`entityTypeKey` is already required, so every typed aggregate has a type), and `behavior(id: String)` is replaced by `behavior(persistenceId: PersistenceId)`, which the gateways call with `PersistenceId(aggregateType.name, aggregateRootId)` (the aggregate id is `persistenceId.entityId`). Bounded adds a factory `AggregateBehavior(persistenceId, emptyState, commandHandler, eventHandler)` that returns a plain `EventSourcedBehavior` with that persistence id and a tagger for the type, so users can still chain `.snapshotWhen`, `.withRetention`, etc. A behavior built by hand must use the given `PersistenceId` and tag with the type; `TestableAggregateRoot` (which captures the real persistence id since item 13) fails a test when the persistence id is not `type|id`, and the docs show the hand-built form.
- **Read side:** `AbstractEventMaterializer` gets `aggregateType: AggregateType`, `CombinedLogicEventMaterializer` gets `aggregateTypes: List[AggregateType]`. Bounded's read journal maps a type to `eventsBySlices(type, 0, numberOfSlices - 1, offset)` on R2DBC and to `eventsByTag(type, offset)` on every other journal. Offsets stay hidden behind `OffsetStore`/`OffsetCodec`; a combined logic's `TagOffsets` is keyed by type name.
- **Test kits:** `TestableProjection.givenEvents(events, aggregateType)` replaces the `tags` parameter; `TestableAggregateRoot` checks the persistence id as above.
- **Raw tags:** `tagName`/`tagNames` are **removed** from the materializers (decided in the implementation). Keeping them deprecated next to `aggregateType` needs an "either one or the other" member, which Scala cannot express without breaking existing `val tagName = …` overrides anyway, and 2.0.0 breaks every materializer's journal setup regardless. A tag of `tags(event)` that is not a type can still be read straight from the read journal. On a tag-based journal every classic event is persisted as `Tagged`, so a write-side event adapter bound to the user's event class does not apply there (it would see `Tagged`); tags belong in `tags(event)`. Typed behaviors keep tagging with the type on every journal: `AggregateBehavior` has no access to the journal config, and typed event adapters (`.eventAdapter`) run before tagging.
- **Left out:** tags on a subset of a type's events or across types on R2DBC. Read the type and filter with `MaterializerEventFilter`, or list several types in a combined logic.

### Migrating existing journals: `AggregateTypeMigration`

A class in `bounded-core` (`io.cafienne.bounded.migration.AggregateTypeMigration`) that converts a journal written without aggregate types (Bounded 1.0.0 and earlier: unprefixed ids, other prefixes, typed `PersistenceId.ofUniqueId`) into `type|id` streams tagged with the type. It runs in the application's own `ActorSystem` with the production journal and snapshot config, and uses only Pekko persistence and query APIs, so one implementation covers LevelDB, in-memory, Cassandra, JDBC and R2DBC. No in-place SQL: R2DBC's `slice` is a JVM hash of the persistence id and Cassandra's partition key is the persistence id, so copying is the portable route.

- **Input:** a rule per event, `(oldPersistenceId, event) => Option[MigrationTarget(aggregateType, aggregateId, tags)]` (`byPrefix`, `byEvent`, and `withTags` to add extra tags, which are not copied by themselves because the queries do not return them). `None` leaves the event's stream alone and reports it.
- **Which streams:** by default all ids from `currentPersistenceIds` (offered by every supported read journal), including 1.0.0 streams with a prefix such as `Order|`. A stream the rule maps onto itself is *in place*; on a tag-based journal the report counts its events that lack the type tag (`untagged`), which copying cannot fix in place.
- **Conflicts:** a plan where two old streams share a target, or a target is itself an old stream that is migrated, is refused before anything is written.
- **Copy:** read the old stream with `currentEventsByPersistenceId` and write each target stream through a short-lived `PersistentActor` with the new persistence id (`persistAll` of `Tagged(event, Set(type) ++ extra tags)` on tag-based journals, of the bare event on R2DBC without extra tags, in batches; a rejected write fails the copy), so tags, `entity_type` and `slice` are set by the journal itself. Sequence numbers start at 1 in the target, in the original order. Write timestamps (and JDBC ordering / R2DBC `db_timestamp`) are new; classic event metadata is not copied.
- **Mixed streams (W4):** a stream whose events map to several types is split into one stream per type, renumbered per target, and reported.
- **Snapshots:** the latest snapshot is copied to the new id at the same sequence number when the stream is not split; for a split stream it is dropped and recovery replays the events. When the events up to the snapshot were deleted, the snapshot is written before the first remaining event, so recovery still works.
- **Safe to rerun:** an interrupted run resumes: events a target already holds are compared with the source events for the same sequence numbers (equal, or the same serialized bytes) and skipped. A target holding other events, more events than its source gives it, or a gap fails the copy instead of being trusted.
- **Dry run:** reports, without writing, the target of every stream, event counts, splits, snapshot handling and events the rule does not map.
- **Verify, then delete:** after copying, compare the number of stored events and the last sequence number per target with the plan; a separate `deleteMigrated()` deletes the old streams (and their snapshots, when a snapshot store is configured) via the journal, each within the migration's timeout. Until then old and new rows coexist, and on tag-based journals old events may carry the same tag (e.g. from an event adapter), so materializers must not replay before the delete.
- **Leftover tags:** `oldStreamsReadableByType(types)` lists, per type, the old streams whose events can still be read under that type's tag after the delete. Journals that keep deleted events in their tag queries (Cassandra's tag views, the in-memory journal) return old events that already carried the type's name as a tag, so it must be empty before materializers start; on Cassandra clean the tag views with the plugin's reconciliation tool. Always empty on R2DBC, which reads by entity type.
- **Offsets:** the copies have new offsets, so a materializer left as it is handles all of them. Combined logic uses `startCombinedLogicAtEnd(store, viewIdentifier, types)` (TagOffsets at the last event of each type) so they do not repeat side effects; materializers that keep their data use `startAtEnd(store, viewIdentifier, type)`; those rebuilt from scratch use `resetOffsets(store, viewIdentifiers)` (`NoOffset`). On R2DBC the end offset is moved `backtracking.window` + `behind-current-time` (+1s) past the last copy, because a reader backtracks that far before its start offset, and the call waits until that moment has passed.
- **Runs offline:** no aggregate, gateway or materializer may run during the copy, or writes to the old ids are lost; the docs give the order: stop the application, dry run, migrate, verify, delete, check leftover tags, set the offsets, start the new version.

## Order of work

Items are numbered in the order they should be done. Within milestone 1 the order is set by four dependencies:

- **Cassandra store (3) before restart and offsets (5).** Today a failed Cassandra offset save is silently ignored, and with B9 every save fails when the keyspace is not `akka`. Once item 5 makes a failed save fail the stream, those users would restart on the first event until restarts run out. Do not tag a release between 3 and 5.
- **Offset encoder (4) before the combined logic (7).** Both change how every store turns an offset into text. Doing the encoder first means the stores are rewritten once, and it fixes most of R4 on the way.
- **Restart and offsets (5) before the combined logic (7).** The combined logic needs per-tag resume state, so item 5 builds its in-memory resume state so it can hold one offset per tag from the start.
- **Filter cast (6) right after 5.** Same pipeline lines, and saving the offset of filtered-out events needs item 5's chained save. It is P2 by impact but only a few lines at this point.

## Breaking changes and release

`v1.0.0` (Pekko, Scala 2.13) is released and contains the items marked **Done**; the table lists the breaking changes it shipped. Item 21 breaks the 1.0.0 API and requires a journal migration for most users, so it goes into the next major release, 2.0.0, which is also the first Scala 3 release; it is merged to `main` but not yet released:

| Item | Change users notice |
| --- | --- |
| 1 | Classic replies arrive after the events are stored, and persist failures now return `Ko` instead of `Ok` |
| 5 | The `registerListener` future completes only on stop (it used to always fail with `ClassCastException`) or fails when restarts are used up; handlers can see an event more than once after a restart; restart behaviour is configured under `bounded.eventmaterializers.restart` |
| 7 | Combined logic offsets are stored as `TagOffsets`; old values are read, but an older Bounded cannot read the new ones |
| 8 | `DefaultCommandGateway` is deprecated |
| 16 | Classic aggregates with `snapShotInterval` now delete their older snapshots; set `deleteOlderSnapshots = false` to keep them |
| 18 | Custom `OffsetStore`s and materializers that relied on the `???` defaults no longer compile; a materializer class whose store is mixed in at `new` (`new MyMaterializer(system) with OffsetStoreProvider`) must be declared `abstract`. Typed `ask` now runs the `ValidateableCommand` it was always given, and `shutdown()` now waits for the aggregates to stop |
| 21 (2.0.0) | Every aggregate needs an aggregate type: classic `AggregateRootActor`s must define `aggregateType` (`persistenceIdPrefix` is gone), typed managers implement `behavior(persistenceId: PersistenceId)` instead of `behavior(id)` and use the given id. Persistence ids become `type|id`: aggregates that used prefix `type|` in 1.0.0 keep their ids, all others run `AggregateTypeMigration` before upgrading, and every materializer and combined logic gets its offset set (to the end, or reset for a rebuild). Materializers select with `aggregateType`/`aggregateTypes`; `tagName`/`tagNames` are removed. On tag-based journals classic events are persisted as `Tagged`, so write-side event adapters bound to an event class no longer apply there; on R2DBC only events with extra tags are. `TestableProjection.givenEvents` takes an aggregate type. On R2DBC a materializer restarted from its offset handles the events of the backtracking window before that offset again (at-least-once) |

Item 3 puts the Cassandra offset table in the journal plugin's keyspace, `pekko` by default. Users coming from the Akka version have their offsets in `akka.vw_offsetstore`: without setting `bounded.eventmaterializers.cassandra-offsetstore.keyspace = "akka"` they replay everything once. Setups with a keyspace other than `akka` lose nothing, because their offsets were never read back. Users of the LMDB offset store (LevelDB journal, or `offsetstore.type = lmdb`) need the `--add-opens` flags of B12 on Java 17+. Items 12, 13, 15, 17, 19 and 22 are additive or opt-in. With item 17, `Ok`, `Ko` and Bounded's failures are serialized by `ReplySerializer` instead of Java serialization wherever they are serialized.

## Test infrastructure

- **Testkits:** `PersistenceTestKit` (items 1, 8, 9, 13), and `TestableAggregateRoot` / `TestableProjection` in `bounded-test`.
- **Databases (item 10):** JDBC is tested on H2 in-process. Postgres (R2DBC) and Cassandra run in containers started by Testcontainers 2.0.5; those specs are canceled when Docker is not available. H2 and the Postgres driver follow the case-engine versions.
- **Cluster (items 15, 17, 22):** `ClusterNodes` in the `bounded-core` tests starts actor systems that form a cluster in one JVM (artery on port 0), with Java serialization off and a shared JDBC journal on in-memory H2. Its test aggregate `Notes` has a hand-written serializer.
- **JVM:** the `bounded-core` tests run in a forked JVM with the `--add-opens` flags lmdbjava needs (B12).
- **CI:** CircleCI runs on a `machine` executor (`ubuntu-2404:current`) so Testcontainers has a Docker daemon, and installs Temurin 25 itself. The config validates with the CircleCI CLI but has not run on CircleCI yet; check the first build, in particular the SonarCloud orb on the machine executor.
